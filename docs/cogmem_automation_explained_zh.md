# CogMem 记忆自动化：谁来调、什么时候调、按什么顺序调

这份说明是写给完全不写代码的人看的。读完应能回答老师这个问题：

> 这些记忆函数是谁调用的？什么时候调用？按什么顺序调用？MemOS / Mem0 的自动化到底在哪里？

---

## 1. 老师问的不是什么

老师问的**不是**：

- 函数名叫什么
- HTTP 地址怎么对应
- 我们注册了几个工具

老师问的是：

**记忆这件事，在一次对话里，是谁动手、什么时候动手、先做什么后做什么。**

MemOS 和 Mem0 真正做成「自动化」的地方，就在这里。不在路由表里。

---

## 2. 先分清三个角色（看懂全文的钥匙）

一次聊天里其实有三方，不要混在一起。

| 角色 | 是谁 | 干什么 |
|---|---|---|
| **用户** | 人 | 打字发消息 |
| **模型** | 大语言模型，负责想和回答 | 看材料、决定怎么答；材料不够时，可以再开口要工具 |
| **插件** | 装在 OpenClaw 聊天软件里的 CogMem 程序 | 在固定时间点自己去搜记忆、存记忆，不用人点，也不用模型开口 |

上次说的「系统」，**就是第三列：OpenClaw 里装着的 CogMem 插件**。

它不是老师，不是模型，也不是你手动点按钮。它是聊天软件后台里、专门管记忆的那一段程序。用户一说话，OpenClaw 会在规定的时间把它叫醒，它就自己干活。

可以用餐厅来记：

- **顾客** = 用户（点菜、说话）
- **厨师** = 模型（看材料、做菜、回答）
- **服务员** = CogMem 插件（顾客一坐下就先把菜单递上桌；吃完再把这桌记到本子上）

「插件自动」= 服务员已经把菜单放桌上了，厨师不用喊。  
「模型调用工具」= 厨师觉得菜单不够，再喊后厨把某道菜的详细做法拿来。

这两件事是两回事。老师问的「谁来调」，答案就是这两种人：**插件** 和 **模型**。

---

## 3. 自动化分两层，不要合成一层讲

两边都**不是**在代码里写死一条流水线：

```text
search → get → timeline → 结束
```

自动化分成两层：

**第一层：插件自己跑。**  
每轮自动搜、自动存。模型不用开口。Mem0 主要做这一层。MemOS 也做了。我们也做了。

**第二层：教模型按规矩自己往下挖。**  
搜索先只给摘要和编号；不够再凭编号去取原文、看时间顺序。MemOS 这一层写得很完整。Mem0 基本不做。我们现在已经按 MemOS 对齐了这一层。

一句话：

> **插件负责：何时开始搜、何时开始存。**  
> **模型负责：搜完如果不够，要不要再往下挖。**

---

## 4. 第一层：插件自动搜、自动存（模型完全不用开口）

用户每说一句话，OpenClaw 会在两个固定时间点叫醒插件。这两个时间点像门铃：

1. **用户话刚发出、模型还没开始想**  
   门铃响 → 插件先去记忆库搜一圈 → 把几条**摘要**塞进模型马上要看的材料里。
2. **模型已经答完**  
   门铃响 → 插件把这一轮对话存进记忆库。聊久了，再整理成长期记忆。

完整一轮是这样的：

```text
用户说话
    ↓
【门铃 1】模型还没开始想
    插件自动搜记忆（用用户刚说的那句话去搜）
    只塞几张「摘要纸条」给模型，不是整本书
    ↓
模型开始看材料、组织回答
    ↓
模型给出回答
    ↓
【门铃 2】模型已经答完
    插件自动把这一轮存起来
    每大约 10 轮，再自动整理成长期记忆
```

对应到老师看到的那些名字：

| 动作 | 谁调 | 模型要不要调 |
|---|---|---|
| 每轮先搜一遍并塞进上下文 | 插件自动 | 不用 |
| 回合结束把对话存进去 | 插件自动 | 不用 |
| 攒够轮次再整理长期记忆 | 插件自动 | 不用 |

这就是「自动化实现这些函数」的一半：

**search 和 add 默认由插件调，不是等模型想起来再调。**

Mem0 也是这一套，更直白：应用程序写死「先 search → 再让模型回答 → 再 add」。`add` 里面还会自动判断：这条是新事实，还是要覆盖旧的。调用方只调一个 add。

---

## 5. 第二层：为什么不一次把全书塞给模型

如果第一层搜完就把所有相关原文一次性塞回去，模型就吃饱了，**几乎不会再去调「取原文」「看时间线」这些工具**。工具注册了也等于摆设。

MemOS 的办法是：**搜索故意只给半成品。**

像图书馆：

1. 管理员先给你几张目录纸条：书名、一两句摘要、编号。
2. 纸条上还写：这些够不够用；如果不够，下一步该借哪一本。
3. 说明书规定：什么情况拿编号去取全书，什么情况把这一章按时间摊开。
4. 你（模型）按说明书决定要不要再借。

对应到我们现在的三个工具：

| 工具 | 像什么 | 给你什么 |
|---|---|---|
| `cogmem_search` | 查目录 | 摘要 + 编号，不是全文 |
| `cogmem_get` | 凭编号取这一本的原文 | 完整内容 |
| `cogmem_timeline` | 把这一章按时间顺序摊开 | 这段经历里先后发生了什么 |

关键设计是：**编号把函数串起来。**

```text
cogmem_search
    返回 id、episode_id
        ├── cogmem_get(id)              取原文
        └── cogmem_timeline(episode_id) 看这段经历的顺序
                └── 其中某条还要原文
                        └── 再 cogmem_get(那条的 id)
```

没有编号，不能跳去 get / timeline。  
调用顺序**不是**程序员写死 `search()` 完立刻 `get()`。  
而是：

1. 搜索故意返回不完整信息（只有摘要）
2. 返回值里带着下一跳要用的编号
3. 说明书（SKILL）规定什么情况调下一跳
4. 模型按这个协议自己决定

MemOS 把这个叫渐进检索。我们按同一套做了。

---

## 6. 我们现在的完整调用顺序（对齐 MemOS）

```text
【第一层：插件自动，每轮都跑，模型不用调】

用户说话
  → 回答前：插件自动搜，注入几条摘要（不是全文）
  → 如果一条都没有：纸条上写「请你自己用短词再搜一次」

【第二层：模型按协议往下走，需要才调】

  1. 自动搜到的摘要不够，或一条都没有
        → 模型自己生成 2～5 个字的短问题
        → 调用 cogmem_search
        → 返回：摘要 + 编号 + 这段经历的编号
               + 够不够用（sufficient）
               + 建议下一步调谁（next_tools）

  2. 摘要看起来对，但要看原文才能答
        → cogmem_get(编号)

  3. 命中带了「这段经历的编号」，需要看先后顺序
        → cogmem_timeline(经历编号)

  4. 时间线里某条还要原文
        → 再 cogmem_get(那条记忆的编号)
```

和 MemOS 是同一套骨架，只是名字不同：

| MemOS | 我们 | 干什么 |
|---|---|---|
| `memory_search` | `cogmem_search` | 只给摘要和编号 |
| `memory_get(chunkId)` | `cogmem_get(编号)` | 取原文 |
| `memory_timeline(chunkId)` | `cogmem_timeline(经历编号)` | 看前后顺序 |
| 还有 task / skill 那一跳 | 没有 | 因为我们的结构是经历（Episode）和轨迹（Trajectory），不是 MemOS 的任务手册 |

五个对外接口没有改。改的是**给模型看的东西**：从「一次喂饱」变成「先给目录，再按编号往下借」。

## 7. 用一个完整例子从头走到尾

用户问：「上次那个部署是卡在哪一步？」

### 第 1 步：插件自动搜（模型还没开口）

用户话一发出，插件就用这句话去记忆库搜。模型此时还没开始想。

插件塞给模型几张纸条，例如：

```text
[episode:E12] 上次部署 redis 超时……
   下一步：cogmem_get ； cogmem_timeline
```

这只是摘要。模型还不知道「卡在哪一步」的完整过程。  
结果里还会写：这些摘要可能不够（`sufficient=false`），建议下一步调 timeline。

### 第 2 步：模型判断「相关，但不够答」

模型按说明书走：命中带了经历编号 E12，问题又是「卡在哪一步」，需要先后顺序。

于是模型调用：`cogmem_timeline(经历编号=E12)`

得到按时间排好的几条：

1. 连机器  
2. 装 redis  
3. 超时  
4. 改端口  

### 第 3 步：其中「超时」那条还要原文

模型再调用：`cogmem_get(编号=M77)`

看到具体报错。这时才回答用户。

全程不是程序员写死「search 完立刻 get」。  
是：**插件先自动给摘要；不够用时，摘要上的编号告诉模型下一跳去哪。**

如果用户问得很长、很散，插件会直接判「不够」，逼模型自己提炼成短词再搜。这和 MemOS「不要拿整段用户原话当检索词」是一个意思。

---

## 8. 说明书里写死的决策树（模型按这个走）

插件不会替模型做完 get / timeline。它只把摘要和提示塞进去。模型按下面这张表决定：

| 遇到什么情况 | 调什么 |
|---|---|
| 自动搜一条都没有，或用户问得很长很散 | 自己生成短词，调 `cogmem_search` |
| 摘要对了，要看原文 | 拿编号调 `cogmem_get` |
| 需要这段经历里先后发生了什么 | 拿经历编号调 `cogmem_timeline` |
| 时间线里某条还要原文 | 再调 `cogmem_get` |
| 短词搜了还是空 | 换词再搜，或先查有没有存过记忆 |
| 聊了很久，短期记录有、长期记忆还没有 | 才需要手动触发一次整理 |

没有从搜索或时间线拿到的编号，不能直接去 get / timeline。

## 9. Mem0、MemOS、我们，差在哪

| | Mem0 | MemOS | CogMem 现在 |
|---|---|---|---|
| 每轮自动搜、自动存 | 有，程序写死 | 有，插件门铃写死 | 有，同样是门铃 |
| 搜索之后还要不要 get / timeline | 通常不要，搜索直接给记忆文本 | 要，搜索只给摘要 | 要，已经改成只给摘要 |
| 谁决定下一跳 | 应用程序 | 模型 + 说明书 | 模型 + 说明书 |
| 记忆长什么样 | 一条条事实 | 片段 → 任务 → 经验手册 | 记忆 → 经历 → 轨迹 |
| 搜完够不够用 | 一般不单独说 | 会判断、会建议下一跳 | 已加上：够不够、下一步建议谁 |

Mem0 的自动化几乎全在第一层：应用代码写死 search → 回答 → add。  
MemOS 两层都做。  
我们以前只做了第一层和工具名单；现在第二层也按 MemOS 对齐了。

---

## 10. 以前和现在差在哪（方便汇报时对照）

| 点 | 以前 | 现在 |
|---|---|---|
| 每轮自动塞给模型的 | 一整包编好的记忆上下文 | 几条短摘要 + 编号 |
| 模型去 search | 几乎等于把全文又给一遍 | 只给摘要和编号 |
| 搜完够不够 | 没人说 | 返回「够不够」 |
| 下一步调谁 | 没人说 | 返回「建议下一步调谁」 |
| 说明书 | 只写「什么时候可以调用」 | 写死决策树：search → get / timeline |
| 对外接口 | 五个 | 还是五个，没变 |

所以：不是多注册几个函数，而是把**调用顺序做成可以执行的协议**。

## 11. 跟老师可以怎么说（完整口头稿）

老师，自动化不在函数名怎么对应网址，而在调用编排：谁来调、什么时候调、按什么顺序调。

一次对话里有三方：用户说话，模型负责回答，CogMem 插件装在 OpenClaw 里负责记忆。我说的「系统」，就是这个插件。

自动化分两层。

第一层和 Mem0、MemOS 一样：用户一发消息，插件自动先搜记忆，把材料塞给模型；模型答完，插件自动再存。search 和 add 默认由插件调，不是等模型想起来。

第二层是 MemOS 真正完整、Mem0 基本没有的部分：搜索故意只给摘要和编号，不够再用编号去取原文、看这段经历的时间顺序。调用顺序由「返回编号 + 下一跳提示 + 说明书」驱动，不是代码里写死 search 完立刻 get。

我们已经按 MemOS 对齐了这两层。五个接口没变，变的是给模型看的东西：从一次喂饱，改成先给目录、再按编号往下借。我们没有 MemOS 的任务手册那一跳，因为我们的结构是经历和轨迹，不是任务和 Skill。

一句话：**插件负责何时开始搜、何时开始存；模型负责搜完要不要再往下挖。**
